# Threat model

Status: design baseline, tests not yet implemented. Date: 2026-10-11. STRIDE: Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege.

## Assets and trust boundaries

Protect customer Entra roles/consent, delegated API/ARM/Graph tokens, API OBO certificate, UAMI authority, AVD registration/admin secrets, immutable plans/approvals, queue/stage state, artifacts and audit data. Boundaries are browser to Entra/API; SWA proxy to API origin; API to queue/state; worker to approval/artifact store and Azure/Graph; customer admin workstation to installation sources and Azure/Graph.

No vendor identity or central tenant service is trusted. Customer Azure/Entra owners can intentionally replace the installation or its grants; that administrative power is a residual boundary, not something portal roles can prevent. Ordinary portal operators must have no direct worker/job/identity/storage administration rights.

## Residual risks and release gates

SWA Static Assets are not a security boundary: a public shell is acceptable only if all data/actions require valid API tokens. Direct-origin access and bearer forwarding through a linked backend need integration proof. Do not remove authentication to resolve incompatibility.

App-only `CloudPC.ReadWrite.All` is broad even if portal actions are narrow. Azure VM/extension writes can execute guest code; RBAC-assignment authority and Container Jobs start/template-write rights can escalate access. Customer Azure/Entra platform administrators are trusted high-privilege actors and must be monitored separately.

Table Storage optimistic concurrency does not make approvals immutable or tamper-evident. Define envelope signing/verification, writer separation and audit retention before Phase 3; keys accessible to a compromised approval API cannot protect against that API's full compromise. Require independent approval/customer review and scoped worker authority to reduce impact, not a claim of cryptographic protection from every admin.

Rechecking live app-role revocation without widening Graph runtime grants needs a concrete design: bounded cached eligibility plus reauthentication, or a separately approved verifier. Treat stale eligibility as blocked, not indefinite consent. Token revocation propagation and customer role changes require documented handling.

All threat tests become release gates for the owning phase in [phases.md](phases.md). No tests, installation or penetration assessment ran against live Azure in this session.
